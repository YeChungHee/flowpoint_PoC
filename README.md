# 플로우포인트 테스트 페이지 (PoC)

276홀딩스 플로우포인트의 **내부 검증용 테스트 페이지**입니다.
업무 솔루션(발주 파일 수집·발주·거래명세서·자금일보)으로 고객이 모이고, 쌓인 거래 데이터로 플로우스코어가 정교해지고, 그 점수로 플로우페이(구매 대행) 심사 리스크가 줄어드는 선순환 구조를 거래 문서·결제 알림까지 한 화면 흐름으로 확인하는 데 씁니다.

이번 판(v8): **처음 보는 사람의 입구와 회사 디자인**입니다. 올려 주신 Apple 페이지 스타일 시안(1a 고객 소개 · 1b 심사역 소개 · 1c 심사 대기)을 테스트 페이지에 옮기고, 화면 전체를 276 디자인 시스템으로 통일했습니다.

1. **276 디자인 시스템 토큰**: 회색 계열(gray 50~900) · 브랜드 파랑 **#2D54D6**(primary-500) · 상태색(성공 · 주의 · 위험, 작은 글자는 대비 4.5:1이 되도록 한 단계 진한 색) · 모서리 **버튼 8px · 카드 10px** · 카드는 1px 회색 테두리 + 얕은 그림자. 다크 모드도 같은 토큰을 다시 연결합니다. apple.com 색과 알약 버튼은 이 토큰으로 바뀌었고, 채움 · 회색 · 글자 버튼 3종은 그대로입니다.
2. **글꼴 Pretendard**: jsDelivr에서 **v1.3.9로 고정**한 가변 글꼴의 필요한 글자만 받는 방식(`pretendardvariable-dynamic-subset`)으로 불러옵니다. 받지 못하면(인터넷 없음 · 차단) 맑은 고딕 → 애플 고딕 → 시스템 글꼴로 자동 대체되어 화면이 깨지지 않습니다(자동 점검에서 글꼴 요청을 막은 실행으로 확인).
3. **고객 소개 페이지(첫 화면, `#intro`)**: "매입과 매출이 자금이 되는 곳." 히어로와 자금일보 미리보기, 업무 도구 4칸, 플로우스코어 큰 점수, 플로우페이 · 유동화 카드, 정책자금 안내. 숫자(잔고 1,000만원 · 7일 들어올 돈 +1,100만원 · 점수 662 · 플로우페이 가능 2,011만원 · 먼저 받기 가능 1,716만원)는 앱 상태에서 계산한 값이라 앱과 항상 같습니다. **무료로 시작하기** → 앱 홈, 한 번 들어간 브라우저는 다음부터 바로 앱 홈(사이드바 로고 · 휴대폰 더보기 → 소개 페이지로 다시 엶).
4. **심사역 소개 페이지(`#intro-review`)**: 소개 페이지 메뉴 **심사역** → "판단은 사람이. 근거는 거래가." 실제 심사 대기 건 미리보기(대기 0건이면 고객사 포트폴리오), 기능 3칸. **관리자 로그인 (테스트)** → 심사역 역할로 바꾸고 심사 대기 화면으로(실제 로그인 없음).
5. **심사 대기 화면 개편(`#review`)**: 위쪽 숫자 4개(대기 금액 · 평균 처리 시간 · 이번 달 처리 · 이슈, 각 ⓘ), 고객사 검색 · 서비스 필터, 심사 목록 표(고객사 · 서비스 · 신청 금액 · 스코어 · 상태 + 줄마다 **반려 · 승인**), 오른쪽 이슈 피드(휴대폰은 목록 아래). 줄을 누르면 기존 심사 상세(AI 검토 보고서). 줄의 승인 · 반려는 **판단 사유 창**을 열고 AI 검토 보고서 근거로 추천 사유를 미리 체크합니다(시나리오: 승인 = 입금 이력 양호 · 세금계산서 미발행). 사유 0개면 확정할 수 없습니다.
6. **로고 14a**: 시안 14a 별자리 마크(64×64, 선 46 · 점 37, 가운데 점 브랜드 파랑) + "Flowpoint" 글자. 사이드바 · 소개 페이지 · 매입처 링크 화면 · 탭 아이콘에 같은 마크.

v8에서 정한 것:
- **첫 화면 규칙**: 주소에 화면 표시가 없고 아직 앱에 들어간 적 없는 기록(`entered: false`)이면 소개 페이지. 무료로 시작하기 · 관리자 로그인 · 처음부터 다시는 `entered: true`. 예전 기록(칸 없음)은 이미 쓰던 사람으로 보고 바로 앱 홈.
- **소개 페이지 숫자 = 시나리오 실제 숫자**(따로 적은 값 없음). 투자사 페이지 · 실제 가입 · 로그인은 제외.
- **화면당 채움 버튼 1개와 줄별 승인의 조화**: 심사 목록의 승인은 채움이 아닌 연한 파랑(색조) 버튼, 반려는 회색. 심사 대기 화면의 채움 버튼은 0개, 사유 창의 확정 버튼 1개만 채움.
- **사유 필수 규칙 유지**: 승인 · 반려 모두 사유 하나 이상, 미리 체크는 추천일 뿐이며 심사역이 풀고 바꿀 수 있음.
- **접근성 유지**: 누를 곳 44px(심사 목록 고객사 버튼도 44px), 대비 4.5:1(라이트 · 다크), 키보드(줄의 고객사 이름에서 Enter → 상세, Esc → 그 줄로).
- 그대로 둔 것: 화면 단순화 규칙(설명은 ⓘ · 상태는 색+단어), 메뉴 구조 · 해시 주소 · `data-act`, v5~v7 기능 전부. 발표 자료 색은 바꾸지 않음.

이전 판(v7): **판단 근거**를 더했습니다. 대표가 "왜 부족한지, 그냥 두면 어떻게 되는지, 무엇을 골랐고 결과가 어땠는지"를 한 흐름으로 확인하고, 숫자를 믿고 결정하고, 그 결정이 플로우스코어의 학습 데이터로 쌓이게 합니다. DFINITE 데모의 "이상 → 이유 → 영향 → 판단" 보드, "합계 일치", "근거 원장" 방식을 빌려 왔습니다.

1. **부족 해결 4단계 (이상 → 이유 → 영향 → 판단)**: 부족 해결 시트 맨 위 단계 표시줄로 구간을 오갑니다(키보드 가능).
   - **이상**: "232만원 부족 · 12월 1일부터 · D-20"(11월 11일에 연 경우).
   - **이유**: 잔고 폭포 그래프 — 오늘 잔고 1,000만원에서 가장 낮은 날(12월 3일)까지 입출금 10건을 건마다 더하고 빼서 최저 −232만원에 도착합니다. 글 대안 "오늘 1,000만원 + 들어올 돈 2,486만원 − 나갈 돈 3,718만원 = 최저 −232만원"과 **합계 일치 ✓**(폭포 합계 = 30일 예측 최저 잔고, 원 단위. 다르면 "차이 N원").
   - **영향**: 아직 바꿀 수 있는 구간(오늘 · 플로우페이 신청 마감 D-17 · 세진화학 결제 · 부족 시작 D-20 · 계산서 기한 D-29)과 조치하지 않으면 생길 일(세진화학 550만원 지급 불가 · 5일 늦게 지급, 플로우스코어 약 −40점, 이용 한도 −1,120만원, 모두 가정값).
   - **판단**: v6 비교표와 추천 1개는 그대로, 추천 카드에 **승인**(신청 시트) · **보류**(사유 하나 필수: 다른 자금으로 해결 · 매입처와 결제일 조정 · 비용 부담 · 기타 메모). 담당자는 승인 자리가 **대표 승인 요청**. 맨 아래 **지난 같은 상황**(결과가 붙은 최근 판단).
2. **합계 일치**: 자금일보 맨 위 기준 줄 아래 "**차이 330만원 · 확인 필요 ›**"(은행 잔고(가정) = 장부 잔고 + 미확인 입금, 시나리오의 ㈜누리 330만원). 누르면 미확인 입금 시트에서 금액이 같은 입금 전 매출 3건 중 이름까지 맞는 **누리상회 330만원**을 추천하고, **연결**하면 그 매출이 입금 확인되며 "**합계 일치 ✓**". 매출 줄에서 누리상회를 입금 확인해도 같은 입금으로 연결됩니다(두 번 잡히지 않음). 미확인 입금은 자금 예측·부족 계산에 넣지 않습니다.
3. **평소 범위 지표**: 자금일보 요약 탭에만 타일 6개(받을 돈 회수 일수 · 연체율 · 계산서 기한 내 발행 · 거래처 쏠림 · 결제 전 매입 · 7일 순유입). 직전 12주와 비교해 벗어난 것만 굵은 주황 숫자(시나리오: **결제 전 매입 4,015만원 · 높음 · 평소 726~2,145만원**), 나머지는 "평소 범위", 기록이 8주 미만이면 "기록 부족". 홈은 숫자 3개 그대로입니다.
4. **근거 원장**: 승인·보류한 판단(시점 · 상황 · 고른 방법과 비용 · 사유 · 결정자)을 기록하고 결과를 나중에 자동으로 붙입니다. 승인 후 신청한 건은 그 신청의 완납 · 연체 · 연체 후 완납, 보류·미신청 건은 부족 시작일 다음 날 부족 해소 / 미해소. **플로우스코어 → 우리 회사 → 근거 원장 · 학습 데이터 N건**(결과가 붙은 기록만 셈)에서 보고, 시나리오에 지난 판단 2건(시나리오용)이 미리 들어 있습니다. 기록·표시만 하며 점수 산식은 바꾸지 않습니다.

v7에서 정한 것 (가정값은 `index.html` 상수):
- **`UNPAID_PENALTY = 40`**: 그냥 두면 못 내는 매입 1건당 플로우스코어 약 −40점으로 봅니다(영향 표의 가정값). 이용 한도는 줄어든 점수로 같은 한도 식((점수 − 500) × 40만원, 계산서 기한 지남이면 × 0.7)을 다시 계산합니다.
- **`FP_APPLY_LEAD = 3`**: 플로우페이 신청 마감 = 매입 결제일 3일 전(가정).
- **`NORM_WEEKS = 12`, `NORM_MIN = 8`**: 평소 범위는 오늘에서 7일씩 앞선 날 12번의 값(그날까지 있던 거래 · 그날 상태로 다시 계산)의 최소~최대. 값이 있는 주가 8주 미만이면 "기록 부족".
- **폭포는 최대 12줄**(`WF_MAX`): 넘으면 같은 날의 가장 작은 두 건부터 "같은 날 N건" 한 줄로 묶고, 합계는 그대로입니다.
- **보류는 사유 하나 필수**, "기타"는 메모 필수. 담당자도 보류는 기록할 수 있고 승인은 대표만.
- **근거 원장 결과 규칙**: 보류·미신청 판단은 부족 시작일 다음 날, 부족 시작일부터 장부 잔고가 0원 아래로 갔거나 판단일~부족 시작일에 결제일인 매입을 못 냈거나 늦게 냈으면 "부족 미해소"(사유가 "매입처와 결제일 조정"이면 늦은 지급은 조정으로 봄), 아니면 "부족 해소". 한 번 붙은 결과는 바꾸지 않습니다.
- **미확인 입금 짝짓기**: 금액이 같은 입금 전 매출이 후보, 보낸 사람 이름이 거래처와 맞는 건을 추천합니다. 이름이 다른 같은 금액 매출을 입금 확인해도 미확인 입금은 그대로입니다.
- 그대로 둔 것: v5·v6 화면 규칙(당시 apple.com 색 · 알약 버튼, v8에서 276 디자인으로 바뀜 · 화면당 채움 1개 · 설명은 ⓘ · 상태는 색+단어), 메뉴 · 해시 주소 · `data-act`, 부족 해결 비교와 추천 규칙(가장 싼 해결책 1개 · 주의 거래처 제외), 묶음 상환. 제외: 심사역 대화형 질의(다음 차례), 실제 은행·홈택스 연동, 점수 산식 변경.

이전 판(v6): **자금이 부족할 때 "무엇으로 메울까"를 한 흐름으로 판단**하게 했습니다. 수집 → 자금일보 → 부족 판단 → 상품 연결이 같은 숫자로 이어집니다.

1. **거래마다 납품·계산서 상태**: 매입·매출 줄에 "납품 전 · 계산서 전"처럼 상태 두 단어와 상태에 맞는 버튼 하나가 붙습니다. 매입 납품 전·계산서 전 → **플로우페이로 결제**, 매입 납품 완료 또는 계산서 받음 → **직접 결제**(지급 완료 처리), 매출 납품 완료·계산서 발행·입금 전 → **먼저 받기**(매출채권 유동화, 그 채권을 미리 고른 신청), 매출 납품 완료·계산서 전 → **계산서 발행**. 납품 상태는 거래명세서·인수증 수집으로 자동 표시하고, 없으면 상세 시트의 **납품 완료**로 직접 확인합니다.
2. **부족 해결 비교**: 홈 오늘 할 일의 "232만원 부족 · 12월 1일부터 · D-20 **[부족 해결]**"(11월 11일에 연 경우)을 누르면 플로우페이와 먼저 받기의 **확보 금액 · 예상 비용 · 부족 해결 여부**가 한 표로 나오고, 해결하는 방법 중 **가장 싼 하나만 추천**합니다(채움 버튼 1개). 부족일 전에 이미 들어올 채권은 "해결 안 됨 · 부족일 전 입금"으로 표시해 효과 없는 선택을 막습니다. 홈 세 번째 카드에 **먼저 받기 가능** 금액이 함께 보입니다.
3. **자금일보 보고서형**: 맨 위 "08:00 기준 · 은행 잔고(연동 예정) · 전일 대비", **요약 · 받을 돈 · 줄 돈** 3탭. 요약은 30일 예측 **두 줄(확실 · 보수)**, 받을 돈은 **나이별 막대(30일 이내 · 31~60일 · 연체)**와 **거래처 쏠림(상위 3곳 비중)**, 줄 돈은 플로우페이 대상 / 직접 결제 묶음. 부족 날짜는 함수 하나로 계산해 **홈 · 자금일보 · 알림이 같은 날짜**를 씁니다.
4. **수집 확장**: **세금계산서(홈택스 연동 예정)** 채널을 더해 거래처·금액이 맞으면 거래에 **자동 연결**(계산서 상태 변경, 승인 불필요), 안 맞으면 승인함에 **새 거래 후보**로 올립니다. 발주에는 **납품 예정일 · 결제 조건 · 요구사항** 칸이 생기고(비어 있으면 "확인 필요"), 승인함 줄 버튼은 **승인** 하나(수정·반려는 상세 시트)입니다.

v6에서 정한 것:
- **유동화(먼저 받기) 예상 비용은 가정값**: 플로우스코어 등급별 월 기본율 A 0.8% · B 1.0% · C 1.2% · D 1.5% × 남은 날수/30. 실제는 평가·조건에 따라 달라지므로 화면에 "예상 · 심사 후 확정"을 붙입니다(ⓘ 안). 플로우페이는 결제 기간 가산율(30일 3.3%)을 비용으로 봅니다.
- **추천은 해결하는 것 중 가장 싼 하나**: 각 방법을 적용한 30일 예측을 다시 계산해 최저 잔고가 0 이상이면 "해결"입니다. 플로우페이 가능 금액은 이용 한도 남은 금액과 묶을 수 있는 미발행 매출 합계 중 작은 값입니다.
- **점수 "주의" 거래처는 추천에서 뺌**: 숫자로는 메워도 "주의 거래처 · 심사 필요"로 표시하고 추천하지 않습니다(시나리오의 브라이트몰).
- **보수적 예측선**: 연체 중이거나 점수 "주의" 거래처의 들어올 돈을 빼고 그립니다. 확실 줄과 갈라지는 날이 그 입금 예정일입니다.
- **세금계산서 짝짓기**: 같은 거래처 · 같은 구분(매입/매출) · 합계 금액이 같으면 가장 오래된 열린 거래에 자동 연결, 한 계산서는 한 번만 연결됩니다. 맞는 거래가 없으면 새 거래 후보가 되고, 승인하면 계산서 발행 상태의 거래로 등록됩니다.
- 그대로 둔 것: v5 화면 규칙(apple.com 색 · 알약 버튼 · 화면당 채움 1개 · 설명은 ⓘ · 상태는 색+단어 · 맑은 고딕), 메뉴 구조, 매출 묶음 상환(입금일 당일 넘김, 7일 유예 후 연체), 역할 3종, 날짜 이동, 해시 주소.

이전 판(v5)의 두 가지:
- **apple.com처럼 단순한 화면**: 고객사 대표가 처음 열어도 "돈이 괜찮은가, 오늘 뭘 해야 하나, 플로우페이 얼마 쓸 수 있나"가 바로 보이도록 화면에는 숫자·상태·버튼만 두고 설명은 ⓘ로 접었습니다. 색은 apple.com 값(바탕 #F5F5F7/#FFFFFF, 글자 #1D1D1F, 파란 버튼 #0071E3, 다크 #000/#1D1D1F·링크 #2997FF), 알약 버튼과 큰 둥근 카드, 화면마다 큰 한 문장 제목. 홈은 숫자 3개와 오늘 할 일 3개, 매입·매출 목록은 한 줄에 버튼 하나(나머지는 줄을 눌러 여는 상세 시트), 입력은 **+ 새 거래** 시트로 옮겼습니다.
- **매출 묶음 상환**: 플로우페이 상환은 신청 때 묶은 매출의 대금으로만 합니다. 묶은 매출 대금이 들어온 날 **오늘 276에 넘길 금액** 시트에서 **276에 넘기기**를 누르고, 납품액(마일리지 차감)을 모두 넘기면 자동으로 **상환 완료**(점수·감사 메일). 입금 예정일 + 7일(유예, 가정값)이 지나도록 넘기지 않으면 자동 **연체**, 연체 뒤에도 다 넘기면 **연체 후 완납**입니다.

> ⚠️ 모든 회사명, 금액, 가산율, 점수 산식은 **테스트용 가정값**입니다. 실제 신용평가나 심사 기준이 아니며, 실제 기업 정보나 개인정보는 넣지 않습니다.

## 여는 방법

`index.html` 파일 하나로 동작합니다. 설치할 것은 없습니다.

- 테스트 페이지 주소: https://yechunghee.github.io/flowpoint_PoC/ (예전 화면이 보이면 Cmd+Shift+R 또는 시크릿 창으로 여세요)
- 또는 파일을 내려받아 브라우저(Chrome, Safari, Edge)로 열면 됩니다.
- 처음 여는 브라우저는 **고객 소개 페이지**가 먼저 열립니다. **무료로 시작하기**를 누르면 앱 홈으로 들어가고, 그 뒤로는 바로 앱 홈이 열립니다(소개 페이지는 사이드바 로고 · 휴대폰 더보기 → 소개 페이지). 심사역 화면은 소개 페이지 메뉴 **심사역 → 관리자 로그인 (테스트)**로도 들어갑니다.
- 입력한 내용은 **그 브라우저에만** 저장됩니다. 다른 사람과 공유되지 않습니다.
- 화면 맨 아래 **처음부터 다시 (시나리오 초기화)** 버튼(휴대폰은 하단 탭 **더보기** 안)을 누르면 가상 시나리오 처음 상태(테스트 날짜·역할 포함)로 돌아갑니다.
- 역할은 3가지입니다. **고객(대표)**(기본), **고객(담당자)**(사이드바 아래 **담당자로 보기**: 수집함 확인·수정만, 신청·최종 승인·전자서명은 "대표 승인 요청"), **심사역**(사이드바 맨 아래 역할 카드 **심사역으로 전환** / **고객(대표)으로 전환**). 휴대폰은 **더보기 → 역할 전환 / 담당자로 보기**입니다. 매입처는 역할이 아니라 `#link/…` 외부용 링크 화면으로 처리합니다.
- **날짜 이동(테스트)**: 맨 아래 막대(휴대폰은 더보기)의 **+1일 · +7일 · +30일** 버튼으로 테스트 날짜를 앞으로 옮겨 상환 매출 알림(D-30·D-7·당일·D+1), 넘김 지연 알림, D+7 뒤 자동 연체, 서명 재알림을 확인합니다. 현재 테스트 날짜가 옆에 보이고, **처음부터 다시**를 누르면 오늘로 돌아갑니다.
- 검증 순서와 회의용 질문은 [`docs` 폴더의 검증-시나리오](docs/)에 있습니다.

신청은 4단계 시트로 나눠 진행합니다.

- 플로우페이(구매 대행형, 납품 전): ① 매입 확인 → ② 상환할 매출 묶기 → ③ 서류 확인 → ④ 납품액·상환 일정 확인 후 신청. 276이 매입처에서 사서 고객사에 납품액으로 판매합니다. 납품액 공급가액 = 매입 공급가액 × (1 + 가산율), 가산율은 결제 기간별 **30일 3.3% · 60일 6.6% · 90일 10%**, 부가세 10%. 결제 기간은 묶은 매출의 가장 늦은 입금일을 덮는 구간으로 제안됩니다. 화면은 세금계산서 형식(공급가액·세액·합계)이며 마지막 단계에 **최종 가격은 영업 담당과 협의 후 확정** 한 줄이 보입니다. 상환은 묶은 매출 대금으로만 합니다: 묶은 매출 합계(부가세 포함)가 넘길 금액(납품액 − 마일리지)보다 적으면 신청할 수 없고, 상환 일정은 입금 예정일 순서로 매출별 넘길 금액을 채웁니다(예: 한결푸드 4,400,000원 → 그린마켓 11,565,090원 = 15,965,090원). 매출처 계좌 변경 통지는 없고, 고객사가 입금일 당일 276에 넘깁니다. 다른 신청에 이미 묶인 매출은 고를 수 없습니다. ③에서 올려야 할 서류가 남아 있으면 버튼이 "서류 N건 남음"으로 막힙니다.
- 매출채권 유동화(납품 후): ① 양도 가능·계좌 변경 확인 → ② 채권 정보 → ③ 서류 확인 → ④ 확인하고 신청. 승인·전자서명 뒤 채무자 통지(승낙 확인)를 거쳐야 자금이 지급됩니다.
- 컴퓨터에서는 Enter로 다음 단계, Esc로 시트를 닫습니다.

글꼴은 Pretendard(가변, jsDelivr에서 v1.3.9 고정 · 필요한 글자만)를 쓰고, 받지 못하면 맑은 고딕 → Apple SD Gothic Neo → 시스템 글꼴로 대체됩니다(아래 외부 서비스). 색 · 모서리 · 그림자는 276 디자인 시스템 토큰(`index.html` 맨 위 `:root`)이고, 다크 모드는 기기 설정을 따라 같은 토큰을 다시 연결합니다.

## 개발 참고

- 한 파일 안에 화면(HTML), 디자인(CSS), 동작(JavaScript)이 모두 들어 있습니다. 밖에서 받아 오는 것은 아래 **외부 서비스** 2가지(글꼴 · 엑셀 읽기)뿐이고, 둘 다 받지 못해도 페이지는 동작합니다. 실제 외부 API(전자서명·알림톡·세금계산서·은행)는 쓰지 않고 화면 시뮬레이션으로 "연동 예정"을 표시합니다.
- 브라우저 저장 칸 `entered`(v8): 앱에 들어간 적 있으면 `true`(첫 화면 규칙). 예전 기록에 없으면 이미 쓰던 사람으로 봅니다.
- 브라우저 저장 키는 `flowpoint-test-v6`이며, 저장 데이터 모양은 `seed()` 함수에서 확인할 수 있습니다.
  - `role`: 현재 역할. 고객 대표(ceo), 고객 담당자(staff), 심사역(reviewer). 예전 기록의 customer는 ceo로 바꿔 읽습니다
  - `dayOffset`: 날짜 이동(테스트) 일수. 모든 날짜 계산(`today0()`)에 더해집니다
  - `purchases`: 발주(매입) 목록. 발주일 `ordered`, 실제 지급일 `paidOn`. 상태는 결제 예정(ordered), 지급 완료(paid), 플로우페이 결제(financed), 플로우페이 상환 완료(repaid). 플로우페이 결제 건은 상환 금액 `repayAmount`·마지막 상환 매출 입금일 `repayDate`, 묶은 매출 `fundSales`, 묶음 상환 연체일 `repayLate`
  - `sales`: 거래명세서(매출) 목록. 발행일 `issued`, 실제 입금일 `paidOn`, 세금계산서 `tax`·`taxOn`, 거래 상대 확인 `confirm`. 상태는 입금 대기(open), 입금 완료(paid), 유동화 완료(factored), 묶음 정산(bundled)
  - `apps`: 플로우페이·유동화 신청. 단계는 거래 상대 확인(confirm), 심사(review), 반려(rejected), 전자서명(sign), 채무자 통지(notice), 집행(done). 심사 판단 `decision`, 상환 결과 `outcome`(repaid, late)와 연체 후 완납일 `lateRepaid`, 자동 정산 표시 `auto`. 플로우페이는 결제 기간 `tier`, 가산율 `rate`, 납품액 `saleSupply`·`saleVat`·`saleTotal`, 결제일 `payDate`, 마일리지 `mileage`, 넘길 금액 `repayTotal`, 유예일 `graceDays`(7), 상환 일정 `alloc`(매출별 `saleId`·`due`·`saleTotal`·`forward`), 넘긴 기록 `fwd`(건별 `saleId`·`amt`·`date`)
  - v6에서 더한 칸(예전 기록은 `load()`에서 채움): 매입 `delivery`(before/done)·`taxIn`(none/received)·`deliveryDue`(납품 예정일)·`terms`(결제 조건)·`note`(요구사항), 매출 `delivery`·`taxRef`(연결된 세금계산서 수집 항목). 수집함 세금계산서 항목은 `doc: 'tax'`, 자동 연결되면 상태 `linked`와 `refId`
  - v7에서 더한 칸(예전 기록은 `load()`에서 채움): `decisions`(근거 원장: `date` · `sf`{`start`, `need`} · `pick`{`kind` fp/ar, `id`, `party`, `amt`, `cost`} · `choice` approve/hold · `reason` · `memo` · `by` ceo/staff · `appId`(승인 후 신청 id) · `result`{`k` repaid/late/lateRepaid/resolved/unresolved, `date`, `note`, `delta`} · 시나리오용은 `seeded: true`, 예전 기록에 없으면 다시 넣음), `bank`(`unmatched` 미확인 입금 {`date`, `amt`, `sender`} · `matched` 연결 기록 {… , `saleId`, `on`}. 예전 기록은 누리상회 330만원이 입금 전이면 미확인 입금 1건, 아니면 0건)
  - `scoreLog`: 사건별 점수 변동 기록 / `disputes`: 이의 제기
  - 새로 더한 칸(예전 기록은 `load()`에서 기본값으로 채움): `inbox`(수집 후보: 원본 파일·확인 필요 표시·상태 new/checked/approved/rejected), `consents`(수집 채널별 동의), `deals`(거래 문서 7종의 상태·보냄/열람/서명/완료 날짜, 입고 사진), `notifications`(상환 알림·넘김 지연·서명 재알림·감사 메일·심사 전달 기록), `issueLog`(심사역 이슈 확인·조치 기록), `lastApprovalPrompt`(역할별 승인 창 표시 날짜)
  - `docs`, `consent`: 기업 서류함과 보관·재사용 동의
  - `mileage`, `log`, `reqs`, `fav`: 마일리지, 입출금 기록, 정보 요청 내역, 관심 지원사업
- 플로우스코어는 규칙 기반 산식입니다. 기본 점수(`BASE`)에 항목별 가감점을 더합니다. 거래처 점수는 `partnerFactors()`, 우리 회사 점수는 `myFactors()`에서 계산하고, 같은 함수에 과거 날짜를 넣어 월별 추이를 만듭니다. 한도는 `limitInfo()`입니다.
- 모든 동작 전후로 점수를 비교해 바뀐 점수만 `scoreLog`에 남깁니다(`logScores()`).
